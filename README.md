# clod

Local exact-version application assembly using Python 3.12, Node.js Ed25519 signatures and Graphviz diagrams.

Run `python3 -m clod --help` from this directory. For other working directories, set `PYTHONPATH` to this checkout.

```sh
python3 -m clod pack SOURCE --store STORE
python3 -m clod inspect DIGEST --store STORE
python3 -m clod bom DIGEST --store STORE --out NAME-VERSION.cdx.json
python3 -m clod fetch NAME@VERSION... --store STORE [--from https://clodhub.com] [--with-dependencies]
python3 -m clod questions RECIPE@VERSION --store STORE [--answers PARTIAL]
python3 -m clod doctor RECIPE@VERSION --store STORE [--answers ANSWERS] [--install]
python3 -m clod space PATH [--need BYTES]
python3 -m clod locks
python3 -m clod lock KIND [--timeout SECONDS] [--purpose TEXT] -- COMMAND ...
python3 -m clod runs
python3 -m clod clean [--apply] [--older-than DURATION]
python3 -m clod design RECIPE@VERSION --store STORE [--answers ANSWERS] [--substitute SLOT=NAME@VERSION]... [--update-policy security=auto,features=manual,preview=hold] --out DEFINITION
python3 -m clod alternatives RECIPE@VERSION SLOT --store STORE [--from https://clodhub.com]
python3 -m clod resolve DEFINITION --catalogue STORE/catalogue.json --out LOCK
python3 -m clod sign STATEMENT --role release --key KEY --out ENVELOPE
python3 -m clod review DIGEST --store STORE --policy POLICY --trusted
python3 -m clod install DEFINITION --lock LOCK --store STORE --policy POLICY --target APP
python3 -m clod verify APP --policy POLICY --trusted
python3 -m clod export APP --out DIAGRAMS
python3 -m clod outdated APP [--from https://clodhub.com]
python3 -m clod propose-update APP (NEXT_DEFINITION | --channel security|features|preview [--from https://clodhub.com]) --store STORE --policy POLICY --trusted --out PROPOSAL
python3 -m clod approve PROPOSAL --key KEY --policy POLICY --out APPROVAL
python3 -m clod apply APP PROPOSAL --approval APPROVAL --policy POLICY
python3 -m clod recover APP
```

Packages are named by package URL, `pkg:clod/<namespace>/<name>` ([FOUNDATIONS.md](FOUNDATIONS.md#package-names)). On the command line NAME is the full name, `<namespace>/<name>`, or `<name>` alone for `com.clodhub`: `python3 -m clod fetch ourpoker-recipe@0.13.0` fetches `pkg:clod/com.clodhub/ourpoker-recipe` version 0.13.0.

Every digest and signature covers RFC 8785 canonical JSON (`clod.model.canonical`); integers outside plus or minus 2^53-1 are refused. `identity.licence` is an SPDX licence expression. [FOUNDATIONS.md](FOUNDATIONS.md) specifies mandatory platform, class, upstream, compatibility and maintenance metadata. [examples/counter/component.json](examples/counter/component.json) is a complete package with digest-bound shared tests that load its actual source module.

`fetch` reads each package's catalogue entry (`/api/recipes/<name>/<version>` for a recipe, else `/api/components/...`, `<name>` being the last segment of the package name), downloads the archive through its `/bundle` link, refuses it unless its SHA-256 equals the catalogue digest and the archive validates, and adds it to the store as `pack` does. From the release named by the entry's `source` it also downloads, when present, `<name>-<version>.release.dsse.json` and `.guardian.dsse.json` into `statements/<digest>/` and the canonical review report `<name>-<version>.review.json` into `reports/<digest>.json`. When that report names retained documents (format 4: `execution-evidence/`, `contexts/`, `authorizations/`), the release must also carry `<name>-<version>.evidence.tar`, a ustar archive of exactly those store-relative paths; each file must hash to its name before it is added to the store, and a missing or different archive is refused. `clod.evidence.pack_evidence(store, report)` builds that archive. `--with-dependencies` follows declared dependencies and, for a recipe, every component its `recipe.json` names at the pinned version.

Each entry of a recipe's `recipe.json` `components` is a slot: `{id, class: {name, version, digest}, preferred: {name, version}, configuration, includedWhen}`. Components declare `implements`; components and recipes carry authoritative descriptors in `classes`, with digest-bound inventories of interface and behaviour files. `clod.recipe.fit(reference, package, authority, targets=None)` checks the exact class, provided and required interfaces, settings and per-interface platform modules. Provider documentation is independent. `design` checks every filled slot and job candidate and validates the selected runtime, framework, shared dependency and stylesheet constraints. `--substitute SLOT=NAME@VERSION` records `selections[SLOT] = {component, version, reason: "substituted"}`. A job candidate names `{component, profile}` and carries `version` when it differs from the preferred package. `alternatives` queries each authoritative class-provided type, fetches candidate archives and returns `[{name, version, fits, reasons}]`.

`questions` prints a recipe's questions (id, question, ask, askAgent, type, options or min/max, default, askWhen) as `questions`, with `toAsk` and `followUps`. `toAsk` lists the questions to put to the person now: those with `ask` `required` whose `askWhen` holds under `--answers PARTIAL` and the defaults, and those with `ask` `unless-settled` that PARTIAL leaves unanswered. `followUps` lists `{id, askWhen, dependsOn}` for each question that only another, still unanswered, question can bring in. An answer in PARTIAL to an unknown question, of the wrong type, outside the options or out of range is refused with `invalid-answer`. `design` applies the recipe evaluation rules 1 to 25 of the component standard (`clod.recipe.evaluate`, CEL conditions included) to the recipe's `recipe.json` and the components' manifests and `suitability.json`, all read from the store archives, and writes the application definition. Unanswered questions take their defaults. When the answers do not give a design it prints `{"ok": false, "errors": [{code, path}]}` and exits 1, writing nothing. `clod.recipe.World.from_directories(recipe, components)` evaluates source trees instead.

Installation runs no package code. Release and guardian attestations must exist before installation. Review runs before guardian signing. Reports preserve required-local, platform and deployed partitions.

A review or verification report lists one result per declared check: `{package, id, scope, status, exitCode, seconds, reason, logDigest, storage, locks}`, with `classEvidence` for a class check and `space` for a check whose reason is `insufficient-space`, or a failed check whose reason is `cleanup-failed` and whose volume also filled. `storage` is `{writtenBytes, keptBytes}`: the bytes the check's private root held when it ended, and the bytes kept because cleanup could not be confirmed (0 or all of them). `locks` lists `{kind, waitedMilliseconds}` for each machine lock the check held (`xcode`, `gradle`, `android-emulator`, `apple-simulator`), in that order. `space` is the admission record `{path, purpose, required, free, margin, reserved}`; `required` and `free` are null when the volume filled during the check rather than at admission. A failed cleanup keeps the root and its reason, `cleanup-failed`, wins over a full volume. A check whose volume filled while it ran stops the rest; each later check is `blocked` with the same `space` record and the report is still written. A check refused at admission is `blocked` alone; later checks are still tried. Reports whose results lack `storage` or `locks` are refused with `report-format-outdated` and must be produced again with a current review.

`doctor` checks the build tools that the design's selected targets need (`toolchains`, see [FOUNDATIONS.md](FOUNDATIONS.md#doctor)); `--install` runs the host's package-manager command for each missing tool.

`bom` writes a CycloneDX 1.6 JSON bill of materials with the wrapper identity (`group` the namespace, `name` and `version`; `purl` and `bom-ref` the versioned package URL; `vcs` and `website` external references, the website being the catalogue page) and licence, archive and file hashes, package dependencies, and every upstream identity, version, licence expression, revision, repository, notice path and delivery kind. Bundled upstream files and build-time lock files are digest-checked during packing and reading. Installation downloads no build dependencies.

Every signature is a DSSE envelope (`payloadType` `application/vnd.in-toto+json`, Ed25519, `keyid` the SHA-256 of the raw 32-byte public key) over an in-toto Statement v1 whose single subject is `{name, digest: {sha256}}`. The policy pins `publicKey` entries per role; the three role key sets must be disjoint, and each role signs only its own predicates:

| Role | Predicate | Subject | What it binds |
|---|---|---|---|
| release | `https://in-toto.io/attestation/release/v0.1` | `<name>-<version>.tar` (the last segment of the package name), the archive digest; annotation `sourceTreeDigest` | `purl` (the versioned package URL, `pkg:clod/com.clodhub/presence@0.11.0`) and `releaseId` (the package name) |
| guardian | SLSA Verification Summary `https://slsa.dev/verification_summary/v1` | the archive | `verifier.id` (`https://clodhub.com/verifier/clod-guardian-review`), `resourceUri` (the versioned package URL), `policy.uri` (`https://clodhub.com/policy/clod-guardian-review/v1`), `verificationResult` `PASSED`, the review report digest in `inputAttestations`, one `verifiedLevels` entry per reviewed scope (`CLOD_REQUIRED_LOCAL`, `CLOD_PLATFORM`, `CLOD_DEPLOYED`), the dependency count in `dependencyLevels.CLOD_RELEASED` |
| owner | `https://clodhub.com/attestation/update-approval/v1` | `proposal.json`, the proposal digest | application, lock, configuration, design, assembly, report, snapshot and stage digests |
| owner | `https://clodhub.com/attestation/execution-authorization/v1` | `assembly`, the assembly digest | run, context, policy, lock and suite-set digests, execution state, granted suites, validity window |

A store keeps `statements/<digest>/release.dsse.json` and `guardian.dsse.json`; `sign` takes an in-toto Statement and writes its envelope. `clod.trust.publish_release` signs an archive; `publish_review(store, ref, report, private_key, *, policy)` validates the complete report and retained evidence before guardian signing. Verification accepts standard or URL-safe base64, requires the canonical (RFC 8785) payload and envelope, a signature from a key pinned for the role whose `keyid` names that key, and exactly the expected predicate; the guardian's dependency count, scope levels and report digest must match the archive's own review binding, and the report binds the exact dependency digests. `approve` writes one envelope (`APPROVAL`), as does `authorize-execution` (`AUTHORIZATION`).

Verification requires explicit `--trusted` and every archive digest in the external policy's `trustedExecution`. `review`, `verify` and `propose-update` accept `--allow-network` for declared network preparation. Each suite receives a fresh writable copy, private home and cache paths and a credential-free environment. Package suites use their retained package root; application suites use the full generated tree. A suite's `tools` pins each tool to a version of one to three integers; components pin `MAJOR.MINOR` (`"python3": "3.12"`, `"node": "26.5"`) or `MAJOR` (`"xcrun": "72"`). Each declared tool is the executable its name finds on the user's PATH; a version-manager shim (pyenv, rbenv, nodenv, goenv, jenv, asdf, mise) is replaced by the executable the manager's `which` selects, so the suite runs the real interpreter, not the shim. The installed tool matches when the first version in its `--version` (or `-version`) output starts with the pin's components; otherwise the suite is blocked with `tool-version-mismatch`. A `prepare` step that declares `network: true` (dependency installation such as `npm ci`) runs only with `--allow-network`; without it the suite is blocked with `preparation-network-not-authorized`. Preparation logs are separate entries in each suite's content-addressed log index. This is trusted execution, not an operating-system sandbox: trusted code can access the host filesystem and network. Deployed checks remain blocked without authorization.

Only `external:<slug>` execution prerequisites are accepted. Unknown forms reject manifest validation. A check that lists prerequisites but has no `execution` declaration is blocked. A check with an `execution` declaration (report format 4) can use an externally supplied, owner-authorized context; actual validators check its tools, resources, destinations and permitted operations. Ordinary local coverage uses an empty requirements list. There is no passed-prerequisite override.

A `requires` entry in a component or recipe manifest has fields `id type version path` and an optional boolean `optional` (default false; a non-boolean is rejected; `provides` entries refuse it). Install and design validation demand a connection only for a requirement that is not optional; a connected optional requirement is still checked for type and version. For `optional: true` the package's visual definition must declare the input port with `required: false`, and the diagram draws it as optional.

A component installs into the slot the design gives it: an artefact destination must start with `components/<package short name>/`, and clod writes it at `components/<slot id>/` (the design's instance id), so any component filling the slot lands in the same place; the assembly record, diagram and verification use those paths. A recipe's own artefacts stay outside `components/`. An artefact may carry `component` or `withoutComponent` (not both), naming a slot id of the design or a list of two or more different slot ids. A `component` artefact is installed, staged for updates, recorded and drawn only when every named slot is filled; a `withoutComponent` artefact only when they are not all filled, for example a stand-in module for an optional component. Two artefacts share a destination only when one carries `component: X` and the other `withoutComponent: X` (the same slot or set of slots); any other repeated destination is refused. Ownership and collision checks apply only to installed artefacts. Entries without either field always install.

A definition (format 3) carries `updatePolicy` `{security, features, preview}`, each `auto`, `manual` or `hold` (defaults `auto`, `manual`, `hold`); a format 1 or 2 definition is refused with `definition-format-outdated`. Its `id` defaults to the recipe's `<namespace>.<name>` (`com.clodhub.ourpoker-recipe`). It may carry optional `answers` and `selections` objects of canonical JSON values (each at most 65536 canonical bytes). They are saved unchanged in `.clod/definition.json` and covered by the definition digest and the lock's `definitionDigest`; clod does not interpret them.

## Supplied execution contexts

```sh
python3 -m clod execution-request --review DIGEST --store STORE --context CONTEXT --policy POLICY --execution-state STATE --expires-at UNIX_SECONDS --out REQUEST
python3 -m clod authorize-execution REQUEST --key OWNER_KEY --policy POLICY --out AUTHORIZATION
python3 -m clod review DIGEST --store STORE --policy POLICY --trusted --context CONTEXT --authorization AUTHORIZATION --execution-state STATE
```

For application verification, request authority with `--app APP` instead of `--review DIGEST --store STORE`, then pass the same context/authorization/state arguments to `verify`. Updates use an independently installed preview of the exact proposed assembly to derive authorization, then pass those arguments to `propose-update`. Report digests bind the evidence through ordinary owner approval and recovery.

Repeat `execution-request --suite DIGEST:ID` to select exact verified checks, such as build/unit checks without device creation. Invalid, duplicate, local-only or mode-incompatible selections reject before request/registry creation. Explicit selections are retained in `REQUEST.evidence/selection.json` and rederived when signing. Without `--suite`, all mode-compatible checks are selected. Every declaration still appears in the report; unselected external checks remain blocked for absent authority. The owner signs the currently revalidated request.

Contexts use mode `local`, `simulation` or `live`. Simulation identifies `fixture` or `local-provider`; it cannot pass native platform or deployed partitions. Live execution also requires `--allow-live`, explicit signed operations/origins and separate human authorization. No live access is authorized by the local examples. `--allow-network` remains independently required for declared network preparation.

Each authorization is single-use, bounded to exact package/suite/assembly/context/policy digests and a durable external execution registry. A consumed, interrupted or expired authorization requires a new request. Request evidence contains verified archives and public documents; private secret material stays outside archives, stores and application roots. Optional `--secrets FILE` resolves only the authorized symbolic references and credential versions. Provider/secret-bearing output is suppressed; retained results contain only closed structured assertions and fixed diagnostic codes.

Format-2 validation, preparation and checks share the original suite deadline. A declared maximumSeconds can only shorten it. Every probe receives the positive remaining suite/authorization time; input and result hashing are checked again before success. Cleanup has its separate bound and cannot authorize more test work.

Format-2 evidence lives under `contexts/`, `authorizations/`, `execution-evidence/` and `reports/`, with digest filenames. Retained evidence preserves originating Windows or Unix path syntax without requiring the original host; adoption rechecks the local registry, expiry and resources. Complete blocked/failed partitions remain in the same signed report.

Resource records bind bytes and modes. Read-only Apple/Java inventories record internal links without expanding aliases; Apple may explicitly bind an enclosing `Contents` inventory while keeping `Developer` as its tool path. Copied Android resources reject escaping/cyclic links and materialize ordinary files. Validated input copies remain unchanged; private working Android development-kit/cache copies use fixed protocol paths and are removed by the parent after execution. Resource bounds are 8192 executable entries, 1,000,000 records, 8 GiB/file and 64 GiB total, with a 1 MiB descriptor limit.

`clod.environment.describe_resource(identifier, path, inventory_root=None, executables=None)` constructs resource descriptors with the same inventory used during execution. Unix hosts derive executable paths; Windows requires an explicit executable list. It hashes file contents and can be expensive for complete toolchains. Resource validation never silently drops files or escapes the signed boundary.

Windows verification uses suspended-process Job Object containment and protected private files; native execution must be verified on an actual Windows host. `pack`, `propose-update`, `approve`, `apply` and `recover` run on Windows. Executable flags come from the manifest there, and the same source gives the same archive bytes as on macOS or Linux. Symbolic links, junctions and other reparse points are rejected wherever links are. Whole-tree moves use write-through `MoveFileExW` without replacement, retried for up to five seconds while another process holds a handle inside the tree; the transaction lock is a one-byte region lock. Snapshots record the mode Windows reports, so a read-only attribute change invalidates approval while POSIX execute bits do not exist. The actual-host regression in `tests/windows/` is explicitly skipped on other hosts; simulated branches do not establish native success.

On supported 64-bit macOS and Linux with the GNU C library, the runner observes child exit without reaping, finishes owned-group signals and checks, then reaps once. Default child-signal handling and exclusive ownership of child waits are required. Cooperating commands must remain in that group; deliberate session escape remains an expected failing boundary test, not a containment guarantee. Browser checks must use the shared non-detached launcher with executable/profile paths inside runner-issued `CLOD_PRIVATE_ROOT`. Failed cleanup retains private files for inspection and records their location in the step index; secret-material removal is attempted independently.

`python3 -m clod.test_identities /absolute/temporary/identities` generates three disposable private keys and an external policy. Add reviewed archive digests to `trustedExecution` before execution. Keep this directory outside package trees and stores. No identity is a production guardian.

Configuration uses fixed grammars. Secret values are symbolic references and never enter templates. Strings must occupy quoted source/configuration positions; shell templates accept only environment names, identifiers and slugs. Component outputs belong beneath `components/<name>/`; recipe outputs own other generated source. Tests, contracts and fixtures remain under `.clod/packages/<digest>/`. Diagrams load bundled definitions and project integer settings to numeric diagram values.

Stop application processes before applying updates. A sibling `.<name>.clod-transaction/` directory holds the stage, report, proposal, owner approval, lock and durable recovery journal. Owner approval binds the complete original and staged trees, including unmanaged files and metadata. Any observed change invalidates approval. Recovery finds that sibling even when the application directory is absent. Committed backups remain for explicit later cleanup; remove a completed transaction directory only after retaining any required evidence. Cooperating writers use an exclusive lock; uncooperative concurrent edits are unsupported.

Update an installed application with its next definition (for example from `design`); each step refuses unless the previous one succeeded:

```sh
python3 -m clod propose-update APP NEXT_DEFINITION --store STORE --policy POLICY --trusted [--allow-network] --out PROPOSAL
python3 -m clod approve PROPOSAL --key OWNER_KEY --policy POLICY --out APPROVAL
python3 -m clod apply APP PROPOSAL --approval APPROVAL --policy POLICY
python3 -m clod recover APP
```

`propose-update` installs the next assembly into the sibling stage and runs its packages' declared verification checks there, so it needs `--trusted` and every package digest in the policy's `trustedExecution`; without `--trusted` it refuses with `trusted-execution-required` and writes nothing. `apply` checks the owner approval against the unchanged application and stage, then swaps the trees under the journal. `recover` completes or reverses an interrupted `apply` and confirms a committed one.

Update channels: a package's `release` is `{channel, fixes}`. `security` is a patch above 0 on an existing MAJOR.MINOR line and lists one or more advisory ids in `fixes`; `features` is patch 0; `preview` is `MAJOR.MINOR.PATCH-preview.N` (N from 1), which sorts before the release of the same MAJOR.MINOR.PATCH. Pre-releases occur only in package versions and pins, never in class or interface versions. Advisory ids are an upper-case prefix, a hyphen, then letters, digits, `.`, `:`, `_` or `-`, at most 64 characters (GHSA, CVE, PYSEC, RUSTSEC, GO, OSV and the like).

`outdated APP` reads each installed package's `versions` from the catalogue (`/api/{components|recipes}/<name>/latest`) and returns per package `{name, installed, line, policy, security: {version, fixes} | null, features: {version} | null, preview: {version} | null}`, downloading nothing. A listed channel that the version's form does not give is refused with `release-channel`.

`propose-update APP --channel CHANNEL --store STORE` works out the next definition and fetches what it needs into STORE through the `fetch` code path. `security` moves every installed package (the recipe and every slot component, preferred or substituted) to the newest `security` release on its current line, when the result fits: a component release must fit its slot as a substitute would (it implements exactly the slot's class reference), and the recipe's release must leave every installed component, moved or not, fitting its slot; otherwise the component moves are fitted against the installed recipe. A release left out is listed in the proposal's `skipped` as `{name, version, slot, reasons}`. The design's `selections` record each moved version; a package present only as another package's exact `dependencies` pin moves only when that package's own release pins the new version. `features` takes the newest `features` recipe version, and `preview` the newest `features` or `preview` one, with the recorded answers, substitutions and update policy; a package never goes below its installed release on the same MAJOR.MINOR line, so an installed security release newer than the recipe's pin stays when it fits its slot (else `installed-release-unfit`); a recorded substitute that no longer fits its slot stops the proposal with `substitute-unfit` naming the slot. A fetched package whose manifest `release` differs from the catalogue's listing is refused with `release-channel`. A channel whose policy is `hold` is refused with `channel-held`; with nothing newer it is `no-update`. A proposal keeps the installed `updatePolicy`, whatever the next definition carries, unless `propose-update --update-policy security=...,features=...,preview=...` sets one. The proposal (format 2) records `channel` (null for a written definition), that `updatePolicy` and `skipped`; clod takes no other action on `auto` and `manual`. A format 1 proposal is refused with `proposal-format-outdated`.

Run `python3 -m unittest discover -s tests` for local checks. The diagram renderer is vendored; consumers need no sibling checkout. Test modules for the POSIX private-process supervisor, version-manager shims and Darwin discovery skip on Windows. `python -B tests/run_update_cycle.py WORK` packs, reviews, installs and updates a fixture through the command line, then recovers an interrupted apply.

For a dependency-free real package, run `CLOD_REVIEW_SOURCE=/absolute/package python3 -m unittest tests.test_packaged_review -v`. This packs the actual allowlist, creates disposable external identities, performs release-verified review and permits guardian acceptance only after required-local suites pass. Optional `CLOD_REVIEW_EVIDENCE=/absolute/report.json` retains the complete report.

## Disk space, machine locks and cleanup

clod keeps per-user state in `CLOD_STATE_HOME`, by default `~/Library/Application Support/clod` on macOS, `${XDG_STATE_HOME:-~/.local/state}/clod` on Linux and `%LOCALAPPDATA%\clod` on Windows. Errors may carry a `detail` object beside `code` and `path`.

- Admission happens before `fetch`, `pack`, `install`, `propose-update`, `apply` and each check. A check is sized from its copied package or application bytes, the bytes of each resource it copies, 1 GiB for each `npm ci` or `npm install` step, and the fallbacks in `clod/space.py` for Gradle and Apple application builds; an install from three times its archive bytes; a proposal from the install and the current application. A reservation keeps counting its full bytes while the job's own writes also lower the free space, so admission errs on the side of refusing.
- Each check holds the machine locks its declared tools, operations and resources need, from before its first command until it ends. A check holding `android-emulator` receives `CLOD_EMULATOR_PORT`, a console port whose adb port is also free, kept by the lock until the check and its emulator have exited.
- On macOS each check's `CFFIXED_USER_HOME` is its private home, so Xcode DerivedData and SwiftPM caches stay inside the private root; clod's own Xcode destination probes pass `-derivedDataPath` inside it; `xcodebuild -list` refuses that flag without a scheme and writes its DerivedData under the private home. A copied Android SDK or Gradle cache is copied once, into the check's private `protocol/android-sdk-working` or `protocol/gradle-working`; the descriptor names that copy. Package, application and resource copies use APFS clones on macOS and reflinks on Linux where the filesystem allows, else byte copies, with the same digest checks.
- Dependency reuse:
  - npm: a passing check's npm cache content becomes a read-only seed for the rest of the run, in `CLOD_STATE_HOME/seeds/<run>`, only when its bytes match a package-lock SHA-512 integrity. A later check gets a verified copy in its private npm cache. Seeds save downloads, not disk space: each check still writes its own `node_modules`.
  - Swift: a SwiftPM repository becomes a seed for the rest of the run only as a fresh bare repository clod creates from the repository's object files alone, with clod's own configuration and the pinned tag; `git fsck --full --strict` must verify every object and the pinned revision must be complete, at seeding and again at reuse. No configuration, hooks, references or alternates of the check's repository are copied and git is never run on it; without git, Swift seeding is off.
  - Android SDK and Gradle home: each check gets one private writable copy, cloned where the filesystem allows.
  - Gradle seeding is not implemented: Gradle reads a shared cache only with its metadata stores, which no lock pins.
  - Seeds are read-only and removed when the run ends; any change to the seed folder discards every seed. The user's and the system's caches are never read or changed.
- `clod.space.require_space(path, needed_bytes, *, purpose)` refuses with `insufficient-space` and `detail` `{path, purpose, required, free, margin, reserved}` unless the volume holding `path` has `needed_bytes` plus the margin free after other live processes' reservations. The margin is `CLOD_FREE_SPACE_MARGIN` bytes, default 10 GiB. `clod.space.reserve(path, needed_bytes, *, purpose)` admits and holds those bytes for the length of a `with` block; two processes that fit alone but not together cannot both be admitted. A reservation is ignored and removed only when its owner is proved dead. `tree_bytes(path)` measures allocated bytes without following links and refuses more than 2,000,000 entries. Out of space (`ENOSPC`, `EDQUOT`) is always `insufficient-space`. `clod space PATH --need BYTES` prints the numbers and exits 1 when the bytes would not be admitted.
- `clod.locks.heavy(kind, *, purpose, timeout)` holds one machine-wide lock of kind `xcode`, `gradle`, `android-emulator` or `apple-simulator`, re-entrant within a thread. It uses `fcntl.flock` on macOS and Linux and `msvcrt.locking` on Windows, so a dead holder releases it at once. After `timeout` seconds it fails `resource-busy` with `detail.holder` `{pid, processStart, runId, kind, purpose, command, since}`, or null when the record belongs to a dead process. `clod locks` lists holders; `clod lock KIND -- COMMAND ...` runs a command under a lock and exits with its status. `clod.locks.free_port()` picks an emulator console and adb port pair that is free; call it under the `android-emulator` lock.
- `clod.ledger.register(root, kind, *, purpose, keep)` records a root a caller owns (`kind` is `proof` or `work`; `keep` protects it from cleanup); `record` and `finish` do the same for roots clod creates. Each entry holds the root, kind, purpose, run id, pid, process start, creation and end times, bytes at the end, retention reason and references. A root removed at its end drops its entry. `clod runs` lists runs with their remaining roots.
- An owner is dead only when its process start time was recorded, the platform can read start times, and no process with that number and start time runs; anything else counts as alive.
- `clod clean` lists, without changing anything, ledgered roots whose owner is dead and that are not kept, a failed proposal's stage with no journal or backup beside it, and transaction check logs (in the transaction folder's `verification/logs`) no recorded report names. Each entry shows its path, kind, purpose, bytes, owner pid and run id; protected entries also show their reason. Protected and never removed: roots whose owner is alive or unproved dead, kept, pending and journalled roots, any root holding an emulator or simulator profile (`device-profile-present`), any root holding a device or room ownership record unless every device it records is confirmed gone, any root in which a process of this user runs or holds a file open, and every candidate when open files cannot be inspected (`open-files-unknown`). Open files are read with `lsof` on macOS and `/proc/<pid>/fd` on Linux. `clod-*` temporary folders missing from the ledger are listed as unknown and never removed. Stores, recovery backups and journals are never candidates. `--apply` removes exactly the listed plan after rechecking, for each entry, its owner and the open files and processes inside it; refuses with `clean-plan-changed` if the listing changed; makes a dead run's read-only seed folder writable again (only inside `CLOD_STATE_HOME/seeds`); writes a cleanup log with each path, size and ledger entry; and exits 1 listing anything it could not remove. `--older-than` takes `30m`, `12h` or `7d`.
- On Windows, `clod clean` lists what it finds with `removal` set to the reason removal is off: open-file and process detection is not verified there. `--apply` refuses with `clean-removal-off` and removes nothing.
- A root holding an emulator or simulator profile is only ever removed by hand. `clod runs` lists runs and the roots they still own; `clod clean` lists the root with its path, size, owner and the reason `device-profile-present`. To remove one: confirm the owner pid is not running, confirm no emulator, simulator or other process uses the folder (`lsof +D <path>` on macOS or Linux, and `adb devices` or `xcrun simctl list devices` show none of its devices), then delete that one folder. clod then drops its ledger entry at the next `clod clean --apply`.
